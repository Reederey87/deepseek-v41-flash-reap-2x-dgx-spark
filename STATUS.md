**2026-09-12 — The 32-state FP8 indexer page has no DeepGEMM kernel; the kit now carries one (no deploy, no build).** §11.9.15 read DeepGEMM's `block_kv` constraint as a single set, `{32, 64}`, and concluded that `--block-size 64` (pages 64 and 32) was servable. It is not: DeepGEMM gates the paged-MQA path **twice with different sets**, and the assert recorded from the first boot is only the *first* gate. `get_paged_mqa_logits_metadata` asserts `block_kv == 32 or block_kv == 64` (`attention.hpp:262`), but the FP8 logits kernel `fp8_fp4_paged_mqa_logits` has no instantiation for anything but **64** (`attention.hpp:320`). So a 32-state page passes the metadata build and reaches a kernel that does not exist — the engine boots, warms up, and dies on the **first long prompt**. The two gates fail differently enough to matter operationally: a metadata-set miss aborts during `compile_or_warm_up_model` after the weights load, a logits-set miss survives every startup check and fails in production. **No `--block-size` avoids it**: pages are `block_size // compress_ratio` with ratios 1 and 2, so 64 gives `{64, 32}` and 128 gives `{128, 64}`, and 128 is outside *both* sets. **Route C, chosen after exa research and reviewer consultation.** vLLM issue **#53635** (open) lists three options; this kit took the third, a non-DeepGEMM kernel for the unservable page. The alternatives were ruled out on evidence: teaching the arch-12 kernel a 32-state instantiation means a DeepGEMM rebuild this kit cannot ship, and slicing the megapatch's short-row decode top-k (PR **#41834**) is a P1 for the SM120 FP4 indexer path by that patch's own review. **New `overlay/sm12x_mqa.py`** vendors the FP8 paged MQA-logits Triton kernels (paged generic, rowwise, both wrappers, the layout helper) with `fp8_paged_mqa_logits_sm12x` as the entry point; this checkpoint's shape (`H=32, D=128`) takes the **rowwise** path at `BLOCK_N=128, BLOCK_D=64, BLOCK_H=8, num_warps=4`. **New `overlay/patch_sm12x_indexer.py`** installs a hook in `vllm/utils/deep_gemm.py` that runs **before** `_lazy_init()` — so it also holds where the DeepGEMM implementation is absent — and declines unless CUDA, capability family 120, `q[1] is None` (FP8, not MXFP4), the 4D packed page, and `block_kv != 64` all hold; everything else stays on DeepGEMM. The edits are purely additive (no stock line rewritten), so no other platform can shift, and `indexer.py` is untouched because the metadata build needs no change. It **fails closed** on unreviewed state — a page outside the metadata set, a non-`None` `indices` (DeepGEMM's varlen path, which the overlay has no mode for), or a page that is not the 4D packed layout — because it reads the page's value and scale offsets directly, so a layout change would silently misread every scale. **Receipts on the hardware** (GB10 sm_121a, capability 12.1, 48 SMs; `for_review/v41-block-size/DEEPGEMM-ARCH12-FALLBACK-PROBE.txt`): metadata accepted at 32 and 64, logits accepted at 64 and aborting at `attention.hpp:320` at 32; the overlay matches an independent FP32 reference at both geometries (`max_rel 3.665e-05` at 64 states, `3.459e-06` at 32) and matches **DeepGEMM** to `max_rel 7.777e-07` where DeepGEMM can run the same geometry. Beyond-context columns differ deliberately: DeepGEMM leaves them 0 (uncleaned) while the overlay writes `-inf`, and the `-inf` mask equals the beyond-context mask exactly — the strict superset of the `clean_logits=False` contract that makes it safe for the indexer prefill path. The FP8 posture is **structural**: vLLM resolves `indexer_kv_dtype` to `mxfp4` only on capability family 100 and raises outright on sm_120 (`dsa_indexer_uses_fp4`), so no kit-level pin is needed and the fallback is on the critical path rather than dormant. **(P1, the same false acceptance this fixes)** `check_flashinfer_dsv41.py` had one set and therefore called `--block-size 64` **clean** while the ratio-2 pages had no kernel — it would have passed a boot straight into the abort. It now splits the gates (`DEEPGEMM_METADATA_BLOCK_KV`, `DEEPGEMM_FP8_LOGITS_BLOCK_KV`), reports *which* gate rejected a page, and lifts the logits gate only when `sm12x_fallback_installed()` finds the hook in the **installed** `deep_gemm.py`. New `tests/test_sm12x_indexer.py` covers patch application/idempotency/fail-closed, the executed dispatch contract, the vendored module's scope, and the Dockerfile ordering plus the runtime import path (`COPY overlay/` and its directory on `PYTHONPATH`), which is the half the pre-flight cannot check because it runs from the overlay directory. The `patch_v41_kernel_block_size.py` docstring carried the same obsolete single-set reading and is corrected. All eight local suites green, `bash -n` and `shellcheck -S warning` clean, `py_compile` clean. **The CUDA specialist could not run** (model quota exhausted on three attempts), so this kernel-contract change currently rests on the measured receipts above and on `final-reviewer`; that gap is recorded in `RESEARCH.md` §14. **Not rebuilt, not preflighted, not booted** — the fallback has never served a real prompt.

**2026-09-12 — Boot blocker: `--block-size 128` cannot serve this checkpoint. Retargeted to 64 with a new backend patch and a rewritten prefill patch (no deploy, no build).** The warmup abort recorded from the first boot (`RuntimeError: Assertion error (attention.hpp:262): block_kv == 32 or block_kv == 64`, raised from `indexer.py:1268` → `deep_gemm.py:608`) is a **block-size** problem, not a FlashInfer one, and the §11.9.8 fix could not have prevented it. The indexer passes `kv_cache_spec.num_states` to DeepGEMM's paged-MQA kernel as `block_kv`, that kernel is templated for 32 or 64 only, and `num_states = block_size // tokens_per_state` with `tokens_per_state = compress_ratio`. V4.1 carries ratios 1 and 2, so `--block-size 64` gives compressed pages of **64 and 32** (both supported) while 128 gives **128 and 64** (128 has no kernel) — 64 is the checkpoint's native SM12x geometry, and it is the only value the verifier's sweep accepts. **The alternatives are dead ends and upstream agrees:** vLLM issue **#53635** (open, 2026-08-24) reports this exact failure on 2× GB10 and shows PR **#53522**'s `num_states` gate is *insufficient* — gating removes the assert but leaves `schedule_metadata` zero-filled while the decode path still launches `fp8_fp4_paged_mqa_logits`, giving an async IMA; and there is no non-DeepGEMM CUDA fallback in this tree (`sparse_attn_indexer.py:647` launches unconditionally, `:860` raises when `is_cuda() and not has_deep_gemm()`). PR **#53425** is the same direction on the same line (family 120 → `[64]`); it keeps 256 because V4's C128 storage is 2 states, a geometry where the block size is not a lever. **Two code changes.** New `overlay/patch_v41_kernel_block_size.py` adds a capability-family-120 clause returning `[64]` to all three V4.1 backends — they share one KV cache group (`MLAAttentionSpec.is_uniform_with_collection` makes the MLA and indexer specs uniform), and all three advertised 128 on SM121 (`flashinfer_sparse.py` hardcoded, `sparse_mla.py` and `indexer.py` `[64 if family(90) else 128]`), so pinning 64 alone raised `ValueError: No common block size for 64` at engine init. The edits are purely additive, verified as an ordered subsequence of the stock text, so no other platform changes; the patch was validated against the real image source, is idempotent, and all three files compile. `overlay/patch_flashinfer_prefill_pbsx.py` replaces `…pbsx128.py`: at block size 64 the compressed pages are 64 (ratio 1) and 32 (ratio 2, previously missing), so it adds the 32-state instantiation, **keeps** 128 as a compile-time-only hedge, and makes the acceptance test and both dispatch ladders coterminous over `{64, 2, 128, 32}` — the full-tile ladder now ends in an explicit `return false` instead of a bare `else { PBSX(128) }`, removing the trap that made a half-widened guard run the wrong divisor silently. **2026-09-11 — SSH quoting regression in the GPU interlock (no deploy).** The fail-closed interlock added earlier probed the worker with `ssh host docker inspect -f '{{json .HostConfig.DeviceRequests}}' <id>` built as argv. OpenSSH does not forward argv: it joins the arguments with spaces and the remote login shell re-parses the result, so the template split at its space, `docker inspect -f` failed, and **every** start was refused while any container at all was up on the worker (a CPU-only container looked like a docker outage). The previous mock hid this by forwarding argv with `exec "$@"` instead of joining and reparsing. `start.sh` now serializes the whole remote command through `docker_probe()` (`printf '%q ' docker "$@"`), the same mechanism `launch_rank` already used. Added `tests/test_gpu_interlock.sh`, whose ssh stub joins and reparses like the real client, covering nine cases (CPU-only and own-candidate allowed on both nodes; foreign GPU, inspect failure, and unreachable docker refused). Verified: 9/9, `bash -n`, `shellcheck -S warning` clean. GLM untouched; no deploy.

**2026-09-11 — kernel-contract review fixes (no deploy).** Independent review plus a checkpoint-header check found four boot blockers in the kit. (1) The Engram filter ran on the yielded `(name, tensor)` pair, but vLLM's lazy iterator calls `safe_open(...).get_tensor(name)` before yielding, so the 91.55 GiB tables (shards 47–48 of 48) would still be read into UMA; `engram_install.py` now hides Engram names in the wrapped `safe_open` handle's `keys()` and refuses whole-shard loaders while disk is on. (2) This checkpoint stores the MCG marker 0-D (`shape []`; GLM's stores `[1]`), so `_load_exl3`'s strict shape check would abort the first expert; the loader now normalizes a same-numel marker to the packed slot. (3) `vllm serve` forces `VLLM_WORKER_MULTIPROC_METHOD=spawn`, and a spawned worker re-imports `__main__` without its `__main__` block, so the `serve.py`-only install never reached the Engram construction; the image now persists `dsv41_engram.pth` → `dsv41_boot` (the GLM kit's mechanism) and pins spawn. (4) The image copied tests flat to `/opt/dsv41`, but the tests resolve `../overlay`; the Dockerfile now preserves the `overlay/`+`tests/` layout under `/opt/dsv41`. `start.sh` pins `--load-format safetensors --safetensors-load-strategy lazy`, forwards `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS`, and runs `/opt/dsv41/overlay/serve.py`. Tests extended (repo layout and simulated image layout both pass); `docs/KERNELS.md` records the contracts. GLM untouched; no deploy.
